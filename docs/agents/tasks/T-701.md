## Goal (one paragraph, user-visible outcome)

As the person types in the search bar, a dropdown offers brands, product lines ("Samsonite Paralux") and searches other staff ran, from our own index, under their own recent searches. Keyboard and mouse both work, a mistyped brand still finds the brand, and nothing typed ever goes to a third party. The minimal version already works (Claude Code wired `complete` into `SearchBox`); this task makes it look and behave like a finished product.

## Contract (types/endpoints to use; do not change them)

- `GET /api/search/suggest?q=<2–80 chars>` (signed in) → `{ suggestions: { text: string; kind: "brand" | "line" | "search" }[]; ms: number }`; 400 `{ error }` under 2 letters. p95 2.6 ms server-side on the dev DB (`npm run bench:suggest`).
- Today `complete(typed)` returns `string[]` (the `text` fields). Widen it to return the `{ text, kind }` objects (change `page.tsx`'s `complete` only if you need the kind; that one function in `page.tsx` is allowed).

## Requirements (numbered, testable)

1. Rows in this order: matching recent searches (clock icon, max 5), then suggestions (max 8 in all): brand (a tag icon), line (a bag icon), search (the trending icon). The typed part is in normal weight and the rest bold (the existing `highlight`).
2. ↑/↓ move through every row, Enter searches the highlighted row (or the text), Esc closes, Tab leaves the box. `aria-activedescendant`, `role="listbox"` / `option` stay correct; the list is announced (polite) when it changes.
3. A suggestion that arrives after the text changed is never shown (keep the "stale" guard). No request under 2 letters; no request while the same text's answer is on screen.
4. A failed request shows no error: the dropdown simply has no suggestions (autocomplete is a help).
5. 375 px: the dropdown fits the screen width, rows don't wrap into two lines (truncate), touch targets ≥ 40 px high.
6. Dark mode: the dropdown, the highlight and the active row keep WCAG AA contrast.
