## Goal (one paragraph, user-visible outcome)

In /admin → Stores, under the store table, the owner sees "Stores found, not reviewed yet". The owner can record a store someone found (its web address and how it was found) and ask us to check it. A check reads only its robots.txt and terms page, politely. The owner then reads what the check found: whether robots.txt lets our bot read product pages, and the exact sentences from its terms that need reading. Finally the owner approves it for crawling or rejects it. A store that looks like one we already know (e.g. delseyluggagecanada.ca vs delsey.ca) is marked clearly and can only be rejected. Nothing here shows prices; these stores are not searched or crawled.

## Contract (types/endpoints to use; do not change them)

- `GET /api/admin/candidates` → `{ candidates: Candidate[] }`, newest first. `Candidate = { id, name, host, warnings: string[], state, foundVia, note, lookalikeOf, addedAt, probe, decidedBy, decidedAt }`:
  - `state`: `discovered` | `single_page_ok` | `needs_review` | `approved_crawl` | `rejected`
  - `probe`: `null` or `{ at, robots: "allows" | "disallows" | "unreachable", termsUrl, quotes: { category, sentence }[], requests, why: string[] }`
- `POST /api/admin/candidates` `{ url, name?, foundVia: "staff" | "brand_locator" | "link" | "common_crawl", note? }` → 201 `{ candidate }`; 400/409 `{ error }` (plain sentence: e.g. "… is already in the registry as Canada Luggage Depot.")
- `POST /api/admin/candidates/<id>` `{ action: "probe" | "approve" | "reject" }` → `{ candidate }`; 409 `{ error }` (e.g. "Probe the store (robots.txt and terms) before approving it."). A probe can take up to a minute (the store's crawl delay spaces its 2–4 requests).

## Requirements (numbered, testable)

1. A form: web address (required), store name (optional), "How was it found?" (Staff / A brand's store finder / A link on another store / A domain list), note (optional). On success, the new row appears at the top. On an error, show the `error` text under the form.
2. One row per candidate: the name and host (the host as plain text, not a link, so it isn't opened by accident), how it was found, and the date added. Show the state in plain words:
   - `discovered`: "Recorded; not checked yet"
   - `single_page_ok`: "Checked: robots.txt lets us read product pages and the terms quote nothing. Crawling still needs your approval."
   - `needs_review`: "Checked: needs your reading" + `probe.why` as a list
   - `approved_crawl`: "Approved for crawling; an engineer adds it to the registry"
   - `rejected`: "Rejected"
3. When `lookalikeOf` is set (or `warnings` is non-empty), show a warning line above everything in the row: "Looks like {lookalikeOf}. Make sure this is a real, separate store." "Check" and "Approve" are not offered; only "Reject".
4. Probe details, when `probe` is set: "robots.txt: allows / doesn't allow our bot on product pages / couldn't be read"; "Terms page: {termsUrl}" as an external link (`rel="noopener noreferrer"`), or "no terms page found"; each quote as a block quote, verbatim, with its category in plain words (prohibits_automated_access → "about robots and automated access", requires_permission → "needs written permission", non_commercial_only → "personal, non-commercial use only"); "Checked {at as local date and time} · {requests} requests".
5. Actions per row:
   - "Check robots.txt and terms" (probe) for `discovered` / `needs_review` / `single_page_ok`. While it runs: "Checking… this can take up to a minute", with the button disabled.
   - "Approve for crawling" only when `probe` is set and there's no look-alike warning. Confirm in the page first: "Approve {name} for crawling? We'll still only read what robots.txt allows."
   - "Reject" for any state except `rejected` / `approved_crawl`.
   After each action, replace the row with the returned `candidate` and show a toast.
6. Empty state: "No stores waiting. Add one above when you find a store we don't cover."
7. 375 px (no horizontal scroll; quotes wrap), dark mode, keyboard only, visible focus, accessible names.
